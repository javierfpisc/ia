# Automatización de Proxmox VE con Bruno
Esta práctica está diseñada para comprender la automatización de infraestructuras de **Proxmox VE** mediante el paradigma de **Bruno**, un cliente de API de última generación.

## Introducción a Bruno
**Bruno** es una herramienta de código abierto para definir, ejecutar y probar peticiones a interfaces de programación de aplicaciones (API). Utiliza archivos .bru para describir las operaciones que se deben ejecutar, los parámetros necesarios, las cabeceras, la autenticación y las comprobaciones de resultados.
Mediante su interfaz de línea de comandos (CLI), permite ejecutar estas operaciones de forma automatizada, seleccionando el entorno de trabajo y facilitando su integración en scripts y pipelines de CI/CD.
En el ámbito de la automatización de infraestructura, Bruno puede utilizarse para gestionar recursos mediante las API de plataformas como Proxmox, Kubernetes o servicios cloud, siempre que estas expongan las operaciones necesarias. Por ejemplo, una colección de archivos .bru puede definir las operaciones para crear máquinas virtuales, consultar su estado o eliminarlas

### Objetivos y Funcionalidades Clave:

- **Git-Native (nativo de Git):** Almacena las peticiones, colecciones y configuraciones de entorno en archivos de texto legibles dentro del sistema de archivos. Esto permite utilizar Git para el control de versiones, la colaboración y el seguimiento de cambios sin depender de una plataforma externa de sincronización.
- **Seguridad y privacidad local:** Las colecciones se almacenan localmente y Bruno no requiere una cuenta ni sincroniza automáticamente los datos con la nube. Para proteger las credenciales, es necesario gestionar adecuadamente los secretos y evitar incluirlos en archivos compartidos o repositorios.
- **Control de acceso y gestión de secretos:** Facilita el uso de los permisos de los repositorios Git para compartir colecciones con usuarios autorizados. También permite utilizar variables de entorno y mecanismos de gestión de secretos para separar las credenciales de las definiciones de las operaciones.
- **Extensibilidad mediante JavaScript:** Permite ejecutar scripts antes y después de las peticiones para gestionar variables dinámicas, procesar respuestas, encadenar operaciones y automatizar comprobaciones.
- **Automatización mediante CLI:** Permite ejecutar colecciones y operaciones desde la línea de comandos, seleccionando el entorno de destino. Esto facilita la automatización de tareas y su integración en scripts y pipelines de CI/CD, incluidos los flujos de gestión de infraestructura mediante API.

## Despliegue de Infraestructura de Ejemplo
Partimos para realizar esta práctica de los recursos de despliegue disponibles en el directorio **tools/bruno**. Hemos organizado el despliegue de Proxmox en carpetas lógicas. Cada una representa una fase del ciclo de vida de un recurso virtual:

*   **`./environments` (lab.bru):** Archivo fundamental donde definimos las variables de entorno (dirección del host Proxmox, tokens de autenticación, ID del nodo y de la VM) para que el resto de los archivos sean portables.
*   **`./create` (Clone.bru):** Contiene la lógica para invocar la API de Proxmox y generar un clon de una máquina virtual a partir de una plantilla.
*   **`./start` (Start.bru):** Automatiza el encendido del recurso tras su creación.
*   **`./status` (Status.bru):** Consulta el estado actual de la tarea o del recurso en el hipervisor.
*   **`./stop` (Stop.bru):** Realiza un apagado ordenado o forzado del recurso.
*   **`./delete` (Delete.bru):** Se encarga de la limpieza y eliminación de los artefactos creados.

## Ejecución del despliegue
Si bien existen diversos procedimientos, adaptados a cada sistema operativo y gestión de software, para instalar Bruno en la máquina de desarrollo, nosotros usaremos un container docker que nos permitirá independizar la plataforma de ejecución de nuestro código de despligue. Por tanto ejecutaremos una imagen docker para lanzar un container que ejecutará la lógica de invocación a Bruno. Empezamos descargando la última versión de la imagen:
```bash
docker pull usebruno/cli:latest
```
A continuación, desde el directorio **bruno**, lanzamos los distintos objetivos del despliegue.
```bash
docker run -v $(pwd):/bruno usebruno/cli run create --env lab --insecure
docker run -v $(pwd):/bruno usebruno/cli run status --env lab --insecure
docker run -v $(pwd):/bruno usebruno/cli run start --env lab --insecure
docker run -v $(pwd):/bruno usebruno/cli run stop --env lab --insecure
docker run -v $(pwd):/bruno usebruno/cli run delete --env lab --insecure
```
Cada uno de los comandos anteriores se ejecuta según la siguiente estructura sintáctica:

* El parámetro `-v $(pwd):/bruno` monta el directorio de trabajo actual dentro del contenedor en la ruta `/bruno`, permitiendo que Bruno acceda directamente a la colección, las peticiones y los archivos de configuración almacenados en el equipo anfitrión.
* El parámetro **userbruno/cli** corresponde a la imagen docker descargada en el paso anterior.
* La orden `run xxxxx` indica a Bruno que debe ejecutar la petición o carpeta denominada `xxxxx`, mientras que `--env lab` selecciona el entorno `lab`, cargando las variables definidas en dicho entorno, **lab.bru**, durante la ejecución.
* Finalmente, la opción `--insecure` deshabilita la validación de certificados TLS, lo que resulta útil en entornos de laboratorio donde los servidores utilizan certificados autofirmados, como es habitual en instalaciones de Proxmox VE.

La secuencia anterior, ejecuta un ciclo completo de clonado, verificación de estado, arranque, parada y destrucción de una MV a partir de un template de Proxmox.

## Explicación funcional de los artefactos del despliegue
A continuación, se detalla el funcionamiento interno de cada comando definido en los archivos `.bru` para interactuar con la API RESTful de Proxmox.

### Archivo de Entorno de Laboratorio (`lab.bru`)
Su función es definir los valores necesarios para el despliegue (Host del nodo Proxmox, nodo de despliegue, token para autenticación, ID de la MV a crear, ID del template...) que se utilizarán a modo de variables inyectables mediante etiquetas entre llaves (ej: `{{HOST}}`) en los archivos del despliegue.

### Clone VM (`create/Clone.bru`)
Este artefacto es el motor del despliegue masivo. Se encarga de solicitar al hipervisor la creación de una nueva máquina virtual a partir de una plantilla o template. Los parámetros implicados en la acción y explícitos en el archivo de infraestructura correspondiente:

*   **URL de la API:** `{{HOST}}/api2/json/nodes/{{NODE}}/qemu/{{TEMPLATE_VMID}}/clone`.
*   **Funcionamiento Técnico:**
    *   **Método POST:** Al ser una operación que crea un nuevo recurso, se utiliza el método POST enviando los parámetros necesarios en el cuerpo de la petición.
    *   **Parámetros clave:**
        *   `newid`: El nuevo ID que tendrá la máquina virtual (ej. 301).
        *   `name`: El nombre de red/inventario asignado al clon.
        *   `full`: (Valor 0 o 1). Define si se realiza un **clon enlazado** (instantáneo, depende de la plantilla) o un **clon completo** (independiente, copia todos los datos del disco).
        *   `target`: Permite especificar en qué nodo del clúster se desplegará el clon, facilitando el balanceo de carga desde el momento de la creación.
*   **Automatización y Seguimiento:**
    *   Al igual que en los otros archivos `.bru`, este comando incluye un script que captura el **UPID** devuelto por Proxmox. Dado que el clonado (especialmente el "Full Clone") es una tarea asíncrona que puede tardar varios minutos dependiendo de la red y el almacenamiento, el UPID es esencial para que los siguientes pasos de la automatización (como el `Start.bru`) esperen a que el disco esté listo.

### Delete VM (`delete/Delete.bru`)
Este artefacto elimina los recursos creados. Se encarga de solicitar al hipervisor la eliminación de todas las máquinas virtuales definidas en  el archivo de entorno. Los parámetros implicados en la acción:

*   **URL de la API:** `{{HOST}}/json/nodes/{{NODE}}/qemu/{{VMID}}`.
*   **Autenticación:** Utiliza la cabecera `Authorization` con el formato `PVEAPIToken={{TOKEN}}`, lo que permite el acceso *stateless*.
*   **Funcionamiento Técnico:**
    *   **Método DELETE:** Al ser una operación de eliminación invoca ese método HTTP. 

### Start VM (`start/Start.bru`)
Este archivo ejecuta una petición **POST** al endpoint de estado de la máquina virtual.

*   **URL:** `{{HOST}}/api2/json/nodes/{{NODE}}/qemu/{{VMID}}/status/start`.
*   **Autenticación:** Utiliza una cabecera `Authorization` con el formato `PVEAPIToken={{TOKEN}}`, lo que permite el acceso *stateless*.
*   **Script de Post-Respuesta:** Incluye lógica en JavaScript que extrae el **UPID** (Unique Process ID) de la respuesta de Proxmox y lo guarda como una variable (`bru.setVar`). Esto es crítico para monitorizar el progreso de la tarea asíncrona en el servidor.

### Get Status (`status/Status.bru`)
Este elemento utiliza una petición **GET** para obtener información en tiempo real sobre una tarea en curso.

*   **Lógica:** Proxmox devuelve un cuerpo en formato **JSON**. El script integrado en Bruno imprime en la consola el estado de la tarea (HTTP status) y el cuerpo de la respuesta para diagnóstico.

### Stop VM (`stop/Stop.bru`)
Similar al encendido, este artefacto detiene el proceso de la VM.

*   **URL:** `{{HOST}}/api2/json/nodes/{{NODE}}/qemu/{{VMID}}/status/stop`.
*   **Función:** Envía la orden de parada. Al igual que el inicio, captura el UPID resultante para que el administrador sepa si la parada fue exitosa.
