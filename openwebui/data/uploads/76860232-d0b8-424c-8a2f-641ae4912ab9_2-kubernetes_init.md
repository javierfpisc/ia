# Inicialización de Clúster Kubernetes

A continuación se detallan los pasos para la puesta en marcha del clúster y la configuración de los nodos, siguiendo las instrucciones proporcionadas.

## Iniciando k3s

### Inicialización del clúster Kubernetes en kuber1 (nodo Manager)

Ejecutamos como **root:**
```bash
curl -sfL https://get.k3s.io | sh -s - server \
  --flannel-backend=none \
  --disable-network-policy \
  --write-kubeconfig-mode 644 \
  --node-ip=192.168.56.41 \
  --advertise-address=192.168.56.41
```

Como vemos en el comando anterior, k3s se instala ejecutando el script de get.k3s.io y los parámetros que le pasas controlan cómo se configura el cluster en el arranque. El parámetro **server** indica que este nodo será el control-plane (el master), no un worker. Las opciones son las siguientes:

* **--flannel-backend=none** desactiva completamente Flannel, que es el CNI por defecto de k3s. Esto significa que k3s no crea red de pods y espera que instales tú otro CNI como Calico o Cilium. Si no instalas ninguno, el cluster no tendrá red de pods funcional.
* **--disable-network-policy** desactiva el sistema de NetworkPolicy integrado de k3s. Esto se hace normalmente cuando vas a usar Calico u otro CNI que ya gestiona las políticas de red, para evitar conflictos.
* **--write-kubeconfig-mode=644** define los permisos del fichero kubeconfig generado. Con 644 cualquier usuario del sistema puede leerlo y usar kubectl sin ser root.
* **--node-ip=192.168.56.41** fuerza la IP que el nodo usará internamente. Esto evita que k3s seleccione una interfaz incorrecta (por ejemplo NAT o loopback) en máquinas virtuales.
* **--advertise-address=192.168.56.41** indica la IP que el control-plane publica al resto del Cluster, es decir la IP en la que se expone el API server

En conjunto, este comando levanta un control-plane de k3s sin Flannel, con redes de pods y servicios definidas manualmente, y preparado para usar un CNI externo como Calico.

Obtenemos el token de adhesión:
```bash
cat /var/lib/rancher/k3s/server/node-token
```
El Token anterior será necesario para ejecutar los comandos de adhesión en los nodos Worker (kuber2 y kuber3).

### Adhesión al Cluster de los nodos kuber2 y kuber3 (Workers)

En esos nodos, como root, ejecutamos:

En kuber2:
```bash
sudo curl -sfL https://get.k3s.io | K3S_URL=https://192.168.56.41:6443 \
K3S_TOKEN=<TOKEN> INSTALL_K3S_EXEC="--node-ip=192.168.56.42" sh -
```

En kuber3:
```bash
sudo curl -sfL https://get.k3s.io | K3S_URL=https://192.168.56.41:6443 \
K3S_TOKEN=<TOKEN> INSTALL_K3S_EXEC="--node-ip=192.168.56.43" sh -
```

Sustituyendo el valor de **< TOKEN >** Por el valor obtenido en el apartado anterior.

### Comprobando creación del Cluster

Antes de nada desde **kuber1**, en nodo en el que ejecutamos el comando de gestión **kubectl**, ya que en los workers no funcionará, comprobamos la lista de nodos:
```bash
kubectl get nodes
```
Deberíamos de ver los 3 nodos a **Ready**

## Instalación de CNI Calico

Ejecutamos en el nodo Manager (kuber1) con el usuario no root:
```bash
kubectl apply -f \
https://raw.githubusercontent.com/projectcalico/calico/v3.27.0/manifests/calico.yaml
```
La instalación del CNI Calico llevará un tiempo. Podremos comprobar el estado con el comando:
```bash
kubectl get pods -n kube-system | grep calico
```
El estado deseado de esos pods sería **Running**

## Despligue de prueba
A continuación, ya trabajando con un usuario del sistema (por ejemplo vagrant), ejecutaremos un despliegue de prueba para ver que funciona. Creamos en el manager (kuber1) el archivo **nginx.yml** con el contenido:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-test
  labels:
    app: nginx-test
spec:
  replicas: 2
  selector:
    matchLabels:
      app: nginx-test
  template:
    metadata:
      labels:
        app: nginx-test
    spec:
      containers:
      - name: nginx
        image: nginx:stable
        ports:
        - containerPort: 80

---
apiVersion: v1
kind: Service
metadata:
  name: nginx-test-svc
spec:
  selector:
    app: nginx-test
  ports:
  - port: 80
    targetPort: 80
  type: ClusterIP

---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: nginx-test-ingress
  annotations:
    traefik.ingress.kubernetes.io/router.entrypoints: web
spec:
  rules:
  - host: nginx.192.168.56.41.nip.io
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: nginx-test-svc
            port:
              number: 80
```

Lanzamos el despliegue:
```bash
kubectl apply -f nginx.yml
```

Tras el despliegue comprobamos:
```bash
kubectl get pods -A
```

Accediendo a través del Ingress desde navegador del host o curl:
```bash
curl -v http://nginx.192.168.56.41.nip.io
```
Al comando anterior debería de responder el nginx desplegado.
