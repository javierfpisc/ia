# Ansible: Gestión de Configuración para Plataformas de Contenedores

## Introducción a Ansible
Ansible es una herramienta de código abierto diseñada para la automatización de tareas de TI, capaz de realizar desde configuraciones básicas hasta orquestar arquitecturas complejas. Su filosofía principal se basa en el **reducir la complejidad** de los flujos de trabajo y liberar a los administradores de tareas repetitivas.

En el contexto de despliegue de contenedores (Docker, Kubernetes), Ansible deja de ser visto como una simple herramienta de "instalación" para convertirse en el motor que garantiza el estado final del sistema. Su principal objetivo es asegurar que el entorno de TI permanezca **exactamente como se ha definido**, independientemente de cuántos cambios previos se hayan realizado.

---

## El Ciclo de Despliegue (OpenTofu + Ansible)
En nuestro entorno de laboratorio, trabajaremos con Máquinas Virtuales en Proxmox. Para automatizar esto, es fundamental entender cómo encaja Ansible en el ciclo de vida:

1.  **Provisioning (La "Huesped" Virtual):** Imaginemos que usamos **OpenTofu** o scripts de Terraform para generar una Máquina Virtual nueva en Proxmox. Esto nos da un sistema operativo "en blanco".
2.  **Configuración (Ansible):** Es aquí donde entra Ansible. Una vez creada la VM, Ansible se conecta (usando SSH) y asegura que el sistema tenga todo lo necesario para ejecutar contenedores (paquetes instalados, puertos abiertos, configuración de usuarios, instalación de Docker/containerd, etc.).

La principal característica de Ansible es su carácter **idempotente**: si ejecutas el playbook diez veces sobre la misma VM, el resultado será idéntico y no romperá nada si los requisitos ya estaban cumplidos.

## Conceptos y Bondades Clave
A continuación, se detalla por qué Ansible es la herramienta estándar en este tipo de despliegues:

### El Inventory (El Inventario)
El Inventario es el mapa de nuestra red. Es un archivo de texto simple (generalmente en formato .ini o .yml) donde definimos los nombres o direcciones IP de los sistemas que Ansible debe gestionar.

*   **Función:** Le indica a Ansible: "Estos son los hosts remotos a los que tengo autorización para conectar".
*   **Organización:** En los inventarios agruparemos las máquinas por etiquetas (en secciones dentro del archivo de inventario) (ej. `web_servers`, `worker_nodes`) para asignar configuraciones específicas a cada grupo de máquinas.

### Arquitectura "Agentless" (Sin Agentes)
Esta es la característica más valiosa para entornos dinámicos. Ansible se conecta a los nodos remotos a través del protocolo de red estándar **OpenSSH**.

*   **No requiere instalación de Daemon:** No es necesario instalar un servidor (como el agente de Puppet o Chef) en las máquinas virtuales de los alumnos.
*   **Seguridad y Agilidad:** Al aprovechar las credenciales nativas del sistema operativo y el sistema de archivos del host (Control Node), Ansible es descentralizado y reduce la superficie de seguridad.

### Playbooks y Lenguaje Legible
Ansible utiliza YAML para definir sus configuraciones en lo que se llaman archivos de **Playbooks**. Este lenguaje está diseñado para "parecerse a la documentación" y ser entendido tanto por desarrolladores como por administradores de sistemas.

*   **Descripción del Estado:** Un playbook no dice "instala X y luego Y", sino "quiero que el sistema tenga X instalado".
*   **Simplicidad y Orquestación:** Permite describir el entorno, ya sea desde un pequeño *homelab* hasta entornos de gran escala.

### Módulos y Ecosistema
Los **Módulos** son las unidades ejecutables que realizan el trabajo real (módulo `apt` para instalar software, módulo `copy` para subir archivos, etc.). Ansible cuenta con un ecosistema masivo (Ansible Galaxy) y un catálogo de módulos para infraestructura híbrida.

## Conectividad y Requisitos
Una de las mayores ventajas de Ansible es su arquitectura **sin agentes (Agentless)**.

*   **¿Cómo se conecta?:** Ansible se conecta a los sistemas remotos usando el protocolo estándar **OpenSSH**.
*   **Sin instalación previa:** No es necesario instalar ningún "daemon" ni servicio local en la máquina virtual que se va a configurar.
*   **Seguridad:** Se apoya en las credenciales nativas del sistema operativo del usuario (como una clave SSH privada) para controlar el acceso a las máquinas remotas. Esto reduce exponencialmente la complejidad y la superficie de seguridad.

!!!NOTA
       Para que la automatización SSH funcione, cada VM creada por OpenTofu debe tener activo el servicio SSH y las credenciales (usuario/contraseña o claves SSH públicas) accesibles desde la estación de trabajo (Control Node) desde la que se invoque la orquestación de Ansible.

## Uso Básico de la Línea de Comandos (CLI)
Ansible ofrece dos formas básicas de operar:

1.  **Comandos Ad-Hoc:** Consisten en ejecutar una sola línea de comando para hacer una única tarea rápidamente sin necesidad de crear un Playbook completo.
    *   *Ejemplo:* `ansible all -m ping` (Para verificar si todas las VMs están vivas).
    *   *Ejemplo:* `ansible web -m apt -a "name=nginx state=present"` (Para instalar nginx en todos las máquinas etiquetadas en el inventario con "web").
    
2.  **Playbooks (Automatización completa):** Para configuraciones complejas que requieren múltiples pasos, variables y lógicas. Aquí se almacena el proceso y se ejecuta con `ansible-playbook install_containers.yml`.

## Sintaxis y estructura de los elementos principales de despliegue
A continuación se presentan sencillos ejemplos de los archivos principales relacionados con los procesos de automatización Ansible.

### Configuración Básica (`ansible.cfg`)
Ansible busca el archivo de configuración en `/etc/ansible/ansible.cfg`, `~/.ansible.cfg`, o en el directorio actual. Veamos un ejemplo mínimo:
```ini
[defaults]
inventory = ./inventory.ini
remote_user = admin
private_key_file = ~/.ssh/ansible_key
# Desactiva verificación de clave SSH (solo en pruebas)
host_key_checking = False

[privilege_escalation]
become = True
become_method = sudo
become_user = root
```

#### Parámetros útiles:

- **`inventory`**: Ruta al archivo de inventario.
- **`remote_user`**: Usuario SSH predeterminado.
- **`private_key_file`**: Clave SSH para autenticación.
- **`host_key_checking`**: Desactiva la verificación de hosts (no recomendado en producción).

### Archivo de Inventario (`inventory.ini` o `inventory.yml`)
El inventario define los hosts y grupos que Ansible gestionará. Puede ser en formato INI o YAML.

#### Ejemplo en formato INI:
```ini
[web_servers]
web1.example.com ansible_user=admin
web2.example.com ansible_port=2222

[db_servers]
db1.example.com
db2.example.com

[cluster:children]
web_servers
db_servers
```

#### Ejemplo en formato YAML:
```yaml
all:
  children:
    web_servers:
      hosts:
        web1.example.com:
          ansible_user: admin
        web2.example.com:
          ansible_port: 2222
    db_servers:
      hosts:
        db1.example.com:
        db2.example.com:
    cluster:
      children:
        web_servers:
        db_servers:
```

#### Variables en el Inventario:
- Puedes asignar variables directamente a hosts o grupos:
  ```ini
  [web_servers:vars]
  http_port=80
  ```

### Playbooks (`.yml`)
Los playbooks son archivos YAML que describen tareas automatizadas. Veamos un ejemplo de su estructura básica:

```yaml
- name: Configurar servidores web
  hosts: web_servers
  become: yes  # Eleva privilegios (sudo)
  vars:
    package_name: nginx
    config_file: /etc/nginx/nginx.conf

  tasks:
    - name: Instalar Nginx
      ansible.builtin.apt:
        name: "{{ package_name }}"
        state: present
      notify: Reiniciar Nginx

    - name: Copiar configuración
      ansible.builtin.copy:
        src: ./templates/nginx.conf.j2
        dest: "{{ config_file }}"
        owner: root
        group: root
        mode: '0644'

  handlers:
    - name: Reiniciar Nginx
      ansible.builtin.service:
        name: nginx
        state: restarted
```

#### Componentes clave:

1. **`hosts`**: Grupos o hosts del inventario a los que se aplica el playbook.
2. **`vars`**: Variables definidas para el playbook.
3. **`tasks`**: Lista de tareas a ejecutar (módulos de Ansible).
4. **`handlers`**: Acciones que se disparan con `notify` (ej: reiniciar servicios).

## Ejecución desde la CLI. Comandos básicos

1. **Verificar conectividad**:
   ```bash
   ansible all -m ping
   ```
2. **Ejecutar un playbook**:
   ```bash
   ansible-playbook playbook.yml
   ```
3. **Ejecutar una tarea ad-hoc**:
   ```bash
   ansible web_servers -m apt -a "name=nginx state=present"
   ```
4. **Modo de prueba (dry run)**:
   ```bash
   ansible-playbook --check playbook.yml

## Uso Avanzado: Roles Ansible
Un **Role** es una forma estructurada de organizar playbooks, variables, plantillas y archivos en unidades reutilizables y modulares. Su objetivo es simplificar la gestión de configuraciones complejas mediante:

- **Reutilización**: Evita duplicar código en playbooks.
- **Jerarquía clara**: Separa responsabilidades (ej: instalación vs configuración).
- **Portabilidad**: Facilita compartir configuraciones entre proyectos.

### Estructura de un Role
Un Role sigue una estructura de directorios estándar. Ejemplo para un Role llamado `nginx`:
```bash
roles/
└── nginx/
    ├── tasks/           # Tareas principales
    │   └── main.yml
    ├── handlers/        # Handlers (ej: reiniciar servicios)
    │   └── main.yml
    ├── templates/       # Plantillas Jinja2 (ej: nginx.conf.j2)
    │   └── nginx.conf.j2
    ├── files/           # Archivos estáticos (ej: certificados SSL)
    │   └── ssl.crt
    ├── vars/            # Variables específicas del Role
    │   └── main.yml
    ├── defaults/        # Variables por defecto (sobrescribibles)
    │   └── main.yml
    └── meta/            # Dependencias y metadatos
        └── main.yml
```

#### Explicación de la estructura del Role anterior:

1. **`tasks/main.yml`**:  
   Contiene las tareas principales del Role (ej: instalar paquetes, copiar archivos).  
   ```yaml
   - name: Instalar Nginx
     apt:
       name: nginx
       state: present
   ```
2. **`handlers/main.yml`**:  
   Define acciones que se ejecutan al ser notificadas (ej: reiniciar un servicio).  
   ```yaml
   - name: Reiniciar Nginx
     service:
       name: nginx
       state: restarted
   ```
3. **`templates/`**:  
   Almacena plantillas Jinja2 para generar archivos de configuración dinámicos.  
   ```jinja2
   # nginx.conf.j2
   server {
       listen {{ http_port }};  # Variable definida en vars/ o defaults/
   }
   ```
4. **`defaults/main.yml`**:  
   Variables predeterminadas (pueden ser sobrescritas por otros archivos de variables).  
   ```yaml
   http_port: 80
   ```
5. **`meta/main.yml`**:  
   Metadatos como dependencias de otros Roles.  
   ```yaml
   dependencies:
     - { role: common, tags: ['base'] }
   ```

### Uso en Playbooks
Para llamar a un Role en un playbook:
```yaml
- hosts: web_servers
  roles:
    - nginx  # Invoca el Role "nginx"
```

### Ventajas:

- **Variables heredadas**: Las variables en `defaults/` y `vars/` se cargan automáticamente.
- **Orden de ejecución**: Ansible procesa los Roles en el orden definido.

### Ejemplo Práctico
Supongamos que necesitas configurar un servidor web con Nginx y PHP:

1. **Crear Roles separados**:
   - `nginx`: Instala y configura Nginx.
   - `php`: Instala PHP y ajusta `php.ini`.
2. **Playbook principal**:
   ```yaml
   - hosts: webservers
     roles:
       - nginx
       - php
   ```

## Estructura Recomendada para Proyectos
La siguiente estructura es un modelo estándar de organización avanzada de los artefactos de Ansible

```
proyecto_ansible/
├── inventory.ini
├── ansible.cfg
├── playbooks/
│   ├── deploy_web.yml
│   ├── deploy_db.yml
├── roles/
│   ├── nginx/
│   │   ├── tasks/main.yml
│   │   ├── handlers/main.yml
│   │   ├── templates/nginx.conf.j2
├── group_vars/
│   ├── web_servers.yml
│   ├── db_servers.yml
```

- **`roles/`**: Organiza tareas reutilizables.
- **`group_vars/`**: Variables específicas por grupo.
- **`templates/`**: Plantillas Jinja2 para archivos de configuración.

## Procedimientos Prácticos en el Laboratorio
En los despliegues, sobre Proxmox o cualquier otra plataforma, se aplican los siguientes principios de Ansible:

1.  **Inventario:** Definiremos un archivo de texto plano donde listaremos las IPs o hostnames de las máquinas sobre las que vamos a actuar. Ansible leerá esta lista para saber a qué sistemas conectarse.
2.  **Playbook de "Configuración":** Escribiremos una secuencia de tareas (playbook) que, por ejemplo, ejecute las siguientes tareas:
    *   Asegure que se esté ejecutando el SO correcto (Debian/Ubuntu).
    *   Instale las dependencias del motor de contenedores.
    *. Configure las reglas del cortafuegos (UFW/iptables).
    *. Asegure que los contenedores se levanten automáticamente si el servidor se reinicia.
3.  **Verificación (Drift Testing):** Gracias a la naturaleza de Ansible, si se cambia algo manualmente en el servidor y luego vuelve a ejecutar el playbook, Ansible detectará la diferencia (el "drift") y restaurará la configuración deseada automáticamente.

## Conclusión
Dominar Ansible es esencial. Mientras que herramientas como OpenTofu se encargan de **crear** los recursos (las Máquinas Virtuales en Proxmox), Ansible se encarga de **mantenerlos**, configurando el sistema operativo para soportar el entorno de contenedores que estaremos desplegando.
