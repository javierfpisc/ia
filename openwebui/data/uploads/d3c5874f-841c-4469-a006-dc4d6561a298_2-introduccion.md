# Introducción. Infraestructura como Código y Automatización

## El punto de partida: ¿qué problema estamos resolviendo?
En un estado inicial, cuando hemos necesitado una máquina virtual en Proxmox, actuamos un poco del siguiente modo:

1. Entrar en la interfaz web.
2. Pulsar *Create VM*.
3. Rellenar unos 20 campos repartidos en 7 pestañas.
4. Arrancarla, entrar por SSH, actualizar paquetes, instalar Docker, configurar el firewall…
5. Repetir 5 veces si hacen falta 5 nodos.

Funciona. Pero tiene cuatro problemas graves en un entorno profesional:

| Problema | Descripción |
|---|---|
| **No es repetible** | Dentro de tres meses nadie recordará exactamente qué opciones se marcaron. |
| **No es escalable** | Lo que cuesta 15 minutos para una máquina cuesta un día entero para cincuenta. |
| **No es auditable** | No hay registro de quién cambió qué, cuándo ni por qué. |
| **Genera "copos de nieve"** | Cada servidor acaba siendo único e irrepetible, y cuando falla nadie sabe reconstruirlo. |

A esto último se le llama *snowflake server* (servidor copo de nieve), y a la desviación progresiva entre lo que creemos que hay y lo que realmente hay se le llama **deriva de configuración** (*configuration drift*).

## Automatización de infraestructura
**Automatización de infraestructura** es, sencillamente, sustituir tareas manuales repetitivas por procesos que ejecuta una máquina. Es un concepto amplio y gradual. De hecho ya hemos automatizado en la unidad previa. Algunos casos de uso de automatización serían:

- Un script de Bash que crea usuarios.
- Un script de Python contra el API de Proxmox.
- Una colección de Bruno que lanza peticiones al API.

Automatizar aporta velocidad, reducción de errores humanos y consistencia. Pero por sí sola **no garantiza** que el resultado sea reproducible: un script mal escrito, ejecutado dos veces, puede duplicar recursos o dejar el sistema a medias. De ahí nace la idea siguiente.

## Infraestructura como Código (IaC)

### Definición

> **Infraestructura como Código (IaC)** es la práctica de definir, aprovisionar y gestionar la infraestructura de TI —servidores, redes, almacenamiento, balanceadores, contenedores— mediante **ficheros de código legibles por máquina**, tratados con las mismas prácticas de ingeniería que el software: control de versiones, revisión de cambios, pruebas y despliegue automatizado.

Dicho en corto: **si no está en un fichero versionado, no existe.**

### Consecuencias de aplicar esta idea
Al convertir la infraestructura en código, hereda automáticamente todo el ecosistema del desarrollo de software:

- **Git**: historial completo, ramas, *pull requests*, revisión por pares, posibilidad de volver atrás.
- **Documentación viva**: el código *es* la documentación, y siempre está actualizada.
- **Entornos idénticos**: desarrollo, pruebas y producción salen del mismo fichero, cambiando solo variables.
- **Recuperación ante desastres**: si se pierde el clúster, se reconstruye ejecutando el código.
- **CI/CD**: la infraestructura puede desplegarse desde una *pipeline*, igual que una aplicación.

## Cuatro conceptos importantes

### Declarativo frente a imperativo

- **Imperativo** = describo **los pasos**. *"Crea una VM, si ya existe no la crees, luego instala Docker, si ya está no lo instales…"* Esto bien se puede hacer con un script en Python.
- **Declarativo** = describo **el resultado**. *"Quiero 3 VMs con 4 GB de RAM y Docker instalado."* La herramienta calcula sola qué hay que hacer.

**La IaC moderna es mayoritariamente declarativa.**

### Idempotencia
Una operación es **idempotente** si ejecutarla una vez o cien veces produce exactamente el mismo resultado final. Es la propiedad que permite lanzar la misma configuración sin miedo: si todo está ya como debe, la herramienta **no hace nada**.

### Estado deseado y estado real
La herramienta compara continuamente:

```
   ESTADO DESEADO  (tu código)
            vs.
   ESTADO REAL     (lo que hay en Proxmox)
            =
   PLAN DE CAMBIOS (lo que hay que hacer para igualarlos)
```

Corregir automáticamente esa diferencia se llama **reconciliación**.

### Ganado, no mascotas
Filosofía *cattle, not pets*: los servidores no se miman ni se reparan a mano; si uno falla, **se destruye y se vuelve a crear desde el código**. Esto es lo que se conoce como **infraestructura inmutable**, y es la base del mundo de los contenedores (es importante reflexionar un poco sobre este punto, la ironía es buena para entender las cosas).

## Las dos capas del tema: aprovisionar y configurar
No todas las herramientas de IaC hacen lo mismo. Se dividen en dos familias, y en este tema veremos una de cada:

| | **Aprovisionamiento** | **Gestión de la configuración** |
|---|---|---|
| **Pregunta que responde** | ¿Qué máquinas existen? | ¿Qué hay dentro de cada máquina? |
| **Actúa sobre** | El API de la plataforma (Proxmox, AWS…) | El sistema operativo ya arrancado |
| **Herramienta del tema** | **OpenTofu** | **Ansible** |
| **Ejemplo** | Crear 3 VMs con IP fija y 4 GB de RAM | Instalar Docker, abrir puertos, crear usuarios |
| **Estilo** | Declarativo puro, con fichero de estado | Declarativo por tareas, sin estado, sobre SSH |
| **Otras del mismo tipo** | Terraform, Pulumi, CloudFormation | Puppet, Chef, SaltStack |

### Cómo encajan en la cadena completa

```
   [ Código en Git ]
          |
          v
   OpenTofu  ──►  habla con el API de Proxmox  ──►  crea VMs, LXC, redes, discos
          |
          v
   Ansible   ──►  entra por SSH en esas máquinas ──►  instala y configura software
          |
          v
   Docker / Kubernetes  ──►  orquesta los contenedores encima
```

Es importante apreciar en la coherencia con lo ya estudiado: **OpenTofu hace, mediante un plugin llamado *provider*, exactamente las mismas llamadas al API de Proxmox que se pueden programar con Python.** La diferencia es que ese código ya está escrito, probado y es idempotente.

## Por qué OpenTofu y por qué Ansible

- **OpenTofu** es una herramienta de IaC de código abierto, fork de Terraform, alojada bajo la Linux Foundation y con documentación bajo licencia MPL-2.0. Su documentación se organiza en *Getting started*, *The OpenTofu Language*, *The Command Line* e *Internals*, y una de sus piezas clave es el **grafo de dependencias de recursos** que genera para decidir el orden de ejecución.
- **Ansible** es la herramienta de gestión de configuración más extendida: sin agentes, funciona sobre SSH y describe el estado deseado del sistema en ficheros YAML llamados *playbooks*.

Ambas son **abiertas**, **declarativas** e **idempotentes**.

## Vocabulario mínimo antes de empezar

- **IaC**: infraestructura definida en ficheros de código versionados.
- **Aprovisionar**: crear la infraestructura (OpenTofu).
- **Configurar**: preparar el software dentro de ella (Ansible).
- **Declarativo**: se describe el resultado, no los pasos.
- **Idempotente**: repetir la ejecución no altera el resultado.
- **Estado**: inventario de lo que la herramienta ha creado y gestiona.
- **Drift**: divergencia entre lo declarado y lo que existe realmente.
- **Inmutable**: no se modifica, se destruye y se recrea.
- **Provider / módulo / playbook / rol**: unidades reutilizables de cada herramienta.
