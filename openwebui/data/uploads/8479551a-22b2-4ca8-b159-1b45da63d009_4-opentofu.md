# OpenTofu: automatización e Infraestructura como Código (IaC)

## Introducción

### De hacer clic a escribir código
Hasta ahora hemos trabajado con Proxmox de dos formas:

1. **Manualmente**, desde la interfaz web (crear una VM, un contenedor LXC, una red, un disco…).
2. **Programáticamente**, atacando su API con Python y probándola con Bruno.

La segunda opción anterior, la programática, es de por sí automatización, pero el enfoque consiste en indicar **el "cómo"** (haz una petición POST, comprueba el código de respuesta, reintenta, borra si ya existe…). Ese estilo se llama **imperativo**.

La **Infraestructura como Código (IaC)** con OpenTofu, o alguna herramienta similar, cambia el enfoque: describimos **el "qué"** (quiero 3 VMs con 4 GB de RAM en este nodo del clúster) y la herramienta se encarga de averiguar qué llamadas hay que hacer, en qué orden y qué hay que crear, modificar o destruir. Ese estilo se llama **declarativo**.

### ¿Qué es OpenTofu?
OpenTofu es una herramienta de línea de comandos, de código abierto, que permite **describir, crear, modificar y destruir infraestructura** a partir de ficheros de configuración escritos en un lenguaje propio. Algunas ideas clave que conviene clarificar desde el principio:

- Es **open source**: un proyecto de la Linux Foundation (LF Projects) y su documentación y código se distribuyen bajo licencia **MPL-2.0**.
- Nació como **fork de Terraform** cuando este cambió su licencia a BUSL. Por eso la sintaxis, los comandos y los conceptos son prácticamente los mismos: lo que veremos aquí sirve para entender Terraform, y al revés.
- Es **agnóstica del proveedor**: el mismo lenguaje sirve para Proxmox, AWS, Azure, Docker, Kubernetes, GitHub, Cloudflare… gracias al sistema de *providers*.

### Objetivos principales

- Gestionar el **ciclo de vida completo** de la infraestructura (creación, modificación y destrucción).
- Proporcionar un **flujo de trabajo consistente y reproducible** independientemente del proveedor de infraestructura.
- Fomentar la **colaboración en equipos** mediante la integración con sistemas de control de versiones (VCS) y pipelines CI/CD.
- Garantizar la **transparencia y trazabilidad** de los cambios antes de aplicarlos.
- Estandarizar configuraciones mediante **módulos reutilizables**.

### Usos principales

| Caso de uso | Descripción |
|---|---|
| **Aprovisionamiento cloud** | Creación y gestión de recursos en AWS, Azure, GCP, etc. |
| **Infraestructura on-premises** | Gestión de recursos locales mediante APIs (VMware, Proxmox, etc.) |
| **Gestión de Kubernetes** | Despliegue y configuración de clústeres y recursos K8s. |
| **Automatización de redes** | Creación de VPCs, subnets, grupos de seguridad, DNS, etc. |
| **Gestión de SaaS y servicios** | Configuración de herramientas como GitHub, DataDog, Splunk, etc. |
| **Entornos multi-cloud** | Orquestación de recursos en varios proveedores desde una sola configuración. |

### Justificación de su uso
Pensemos en el flujo completo de una plataforma de contenedores:

```
OpenTofu  ->  crea las VMs / LXC / redes / almacenamiento en Proxmox
Ansible   ->  configura el sistema operativo dentro de esas máquinas
Kubernetes/Docker -> orquesta los contenedores encima
```

OpenTofu ocupa la **capa de aprovisionamiento**: construye el "hardware virtual" sobre el que después se montará el clúster de contenedores. Sin esta capa, cada vez que necesitemos rehacer el laboratorio tendríamos que volver a repetir a mano los pasos en la web de Proxmox.

## Funcionalidades principales

### Descripción declarativa del estado deseado
Escribimos el *qué* no *cómo* conseguirlo. Si el fichero dice "3 VMs" y ya existen 2, OpenTofu crea solo la que falta. Esto se conoce como **idempotencia**: ejecutar la misma configuración muchas veces produce siempre el mismo resultado (concepto este de suma importancia).

### Grafo de dependencias
OpenTofu analiza la configuración y construye internamente un **grafo dirigido de dependencias** entre recursos, que después recorre para decidir el orden de ejecución y qué puede hacerse en paralelo. Lo interesante: **normalmente no hay que declarar el orden**. Si una VM referencia el ID de una red, OpenTofu deduce solo que primero hay que crear la red.

### Ciclo plan / apply
Antes de tocar nada, OpenTofu muestra un **plan de ejecución**: qué va a crear (`+`), qué va a modificar (`~`), qué va a destruir (`-`) y qué va a reemplazar (`-/+`). Es una red de seguridad: podemos revisar el impacto antes de romper el clúster.

### Gestión del estado
OpenTofu mantiene un fichero de estado **terraform.tfstate** que actúa como "inventario" de lo que ha creado y de cómo se corresponde con vuestra configuración. Es la pieza que le permite saber qué existe ya y qué hay que cambiar.

### Reutilización mediante módulos
Un conjunto de ficheros de configuración puede empaquetarse como **módulo** y reutilizarse con distintos parámetros: "módulo VM de laboratorio", "módulo nodo worker de Kubernetes", etc.

### Ecosistema de providers y Registry
OpenTofu dispone de un **Registry** propio desde el que se descargan providers y módulos publicados por la comunidad. Para Proxmox existen providers comunitarios (los más usados son los de la familia `bpg/proxmox` y `Telmate/proxmox`); antes de usar uno, conviene consultar siempre su documentación en el Registry, porque los nombres de recursos y argumentos cambian entre ellos.

### Funcionalidades propias de OpenTofu
Como el proyecto evoluciona por su cuenta, ha ido incorporando características que conviene conocer (consultando las notas de la versión utilizada):

- **Cifrado del estado (*state encryption*)**: permite cifrar el fichero de estado, que suele contener datos sensibles.
- **`for_each` en bloques `provider`**: instanciar dinámicamente varios proveedores (por ejemplo, varios clústeres Proxmox) desde la misma configuración.
- **Evaluación temprana de variables** en el bloque `backend` y en los orígenes de los módulos.
- **Opción `-exclude`** en `plan`/`apply`, complementaria a `-target`, para dejar fuera recursos concretos.
- **Soporte de registros OCI** para distribuir providers y módulos en entornos sin acceso a Internet.

## Artefactos: las piezas con las que trabajamos
OpenTofu utiliza su propio **lenguaje declarativo** basado en HCL (*HashiCorp Configuration Language*). Los ficheros de configuración (`.tf`) describen el **estado deseado** de la infraestructura, no los pasos para alcanzarlo. Los elementos sintácticos básicos son:

- **Blocks:** contenedores de configuración que representan objetos (recursos, variables, proveedores...).
- **Arguments:** asignan valores a atributos dentro de un bloque.
- **Expressions:** representan valores, ya sea literales o mediante referencias a otros recursos.

### Resources (Recursos)
Son la **unidad básica de gestión**. Cada bloque `resource` define un objeto de infraestructura concreto (una VM, una VPC, un bucket S3, etc.). OpenTofu construye un **grafo de dependencias** entre recursos para determinar el orden correcto de creación o modificación.

### Modules (Módulos)
Componentes de configuración **reutilizables y parametrizables** que agrupan un conjunto de recursos relacionados. Pueden obtenerse del Registro público de OpenTofu o desarrollarse internamente, promoviendo las buenas prácticas y la estandarización.

### Variables y Outputs
- **Variables:** permiten parametrizar las configuraciones para hacerlas reutilizables.
- **Outputs:** exponen valores de los recursos aprovisionados para su uso en otras configuraciones o módulos.

### Providers
Son **plugins** que traducen los bloques `resource` a llamadas reales a una API. El provider de Proxmox hace exactamente lo que hicimos con Python o Bruno: peticiones HTTP autenticadas a la API de Proxmox. La diferencia es que ya está escrito, probado y gestiona los errores. Se descargan durante `tofu init` y se guardan en el directorio `.terraform/`.

### El fichero de estado (`terraform.tfstate`)
Es el artefacto **más importante y más delicado**:

- Es un **JSON** que asocia cada recurso de nuestra configuración con el objeto real creado (su ID en Proxmox, sus atributos…).
- **Puede contener secretos** en claro (contraseñas, claves). Nunca se sube a un repositorio Git sin cifrar.
- Si se pierde, OpenTofu "olvida" lo que había creado y querrá volver a crearlo todo.
- En trabajo en equipo se guarda en un **backend remoto** (S3, HTTP, etc.) con bloqueo, para que dos personas no apliquen cambios a la vez.

### Ficheros y directorios auxiliares

- `.terraform.lock.hcl`: fija las versiones exactas de los providers. **Sí, es conveniente que se versione en Git**, para que todo el mundo use lo mismo.
- `.terraform/`: caché local de providers y módulos. **No se versiona.**
- `*.tfstate.backup`: copia de seguridad automática del estado anterior.
- Ficheros de plan guardados (`plan.out`): plan binario generado con `tofu plan -out=...`.

## Ficheros de configuración (`.tf`) y lenguaje HCL
Escritos en **HCL** (*HashiCorp Configuration Language*). OpenTofu **carga todos los `.tf` del directorio de trabajo** y los trata como si fueran uno solo, así que la división en ficheros es solo organizativa. Convención habitual:

| Fichero | Contenido típico |
|---|---|
| `main.tf` | Recursos principales |
| `variables.tf` | Declaración de variables de entrada |
| `outputs.tf` | Valores de salida |
| `providers.tf` | Providers y requisitos de versión |
| `terraform.tfvars` | Valores concretos de las variables |

### Bloques del lenguaje HCL

| Bloque | Para qué sirve |
|---|---|
| `terraform` | Configuración de la propia herramienta: versión, providers requeridos, backend |
| `provider` | Cómo conectarse al sistema destino (URL de la API de Proxmox, credenciales…) |
| `resource` | Un objeto de infraestructura que OpenTofu **crea y gestiona** (una VM, un LXC, una red) |
| `data` | Consulta de solo lectura de algo **que ya existe** (una plantilla, un nodo, una imagen) |
| `variable` | Parámetro de entrada |
| `output` | Valor de salida (por ejemplo, la IP de la VM creada) |
| `locals` | Valores intermedios calculados, para no repetirse |
| `module` | Llamada a un conjunto reutilizable de configuración |

### Sintaxis básica HCL

#### Anatomía de un bloque

```hcl
tipo_de_bloque "etiqueta1" "etiqueta2" {
  argumento = valor

  bloque_anidado {
    otro_argumento = valor
  }
}
```

Para un recurso, las dos etiquetas son **tipo de recurso** y **nombre local**:

```hcl
resource "tipo_de_recurso" "nombre_local" {
  ...
}
```

El *nombre local* solo existe dentro de nuestra configuración: es la etiqueta con la que se hará referencia desde otros bloques.

#### Variables, valores y salidas

```hcl
variable "num_nodos" {
  description = "Número de nodos worker a crear"
  type        = number
  default     = 3
}

locals {
  prefijo = "lab-proxmox"
}

output "resumen" {
  value = "Se han creado ${var.num_nodos} nodos con prefijo ${local.prefijo}"
}
```

#### Referencias e interpolación

- A una variable: `var.num_nodos`
- A un valor local: `local.prefijo`
- A un atributo de otro recurso: `tipo_recurso.nombre_local.atributo`
- A un *data source*: `data.tipo.nombre.atributo`
- Interpolación dentro de cadenas: `"${...}"`

**Cada referencia crea automáticamente una dependencia** en el grafo. Si necesitamos una dependencia que no se deduce sola, existe el meta-argumento `depends_on`.

#### Meta-argumentos más habituales

| Meta-argumento | Uso |
|---|---|
| `count` | Crear N copias de un recurso (`count.index` da el número de copia) |
| `for_each` | Crear una copia por cada elemento de un mapa o conjunto (`each.key`, `each.value`) |
| `depends_on` | Forzar un orden que no se deduce de las referencias |
| `provider` | Elegir un provider concreto cuando hay varios configurados |
| `lifecycle` | Reglas especiales: `prevent_destroy`, `create_before_destroy`, `ignore_changes` |

#### Tipos, expresiones y funciones

- **Tipos primitivos**: `string`, `number`, `bool`.
- **Tipos complejos**: `list`, `set`, `map`, `object`, `tuple`.
- **Expresiones**: condicionales (`condicion ? a : b`), bucles (`for`), operadores.
- **Funciones integradas**: `join`, `length`, `format`, `lookup`, `file`, `cidrhost`, `templatefile`… No se pueden definir funciones propias en HCL.
- **Comentarios**: `#` o `//` para una línea, `/* ... */` para varias.

## Ejecución: el ciclo de trabajo

### Comandos esenciales

| Comando | Qué hace |
|---|---|
| `tofu init` | Inicializa el directorio: descarga providers y módulos, configura el backend. **Siempre el primero.** |
| `tofu fmt` | Reformatea los `.tf` al estilo canónico |
| `tofu validate` | Comprueba que la sintaxis y las referencias son correctas (sin llamar a la API) |
| `tofu plan` | Calcula y muestra el plan de cambios, sin aplicarlos |
| `tofu apply` | Aplica los cambios (pide confirmación salvo `-auto-approve`) |
| `tofu destroy` | Destruye toda la infraestructura gestionada |
| `tofu show` | Muestra el estado o un plan guardado en formato legible |
| `tofu output` | Muestra los valores de salida |
| `tofu state list / show` | Inspecciona el estado recurso a recurso |
| `tofu import` | Incorpora al estado un recurso creado previamente a mano |
| `tofu console` | Consola interactiva para probar expresiones y funciones |

### El ciclo habitual

```
        escribir .tf
             |
             v
        tofu init        (una vez, o al cambiar providers/backend)
             |
             v
        tofu fmt + validate
             |
             v
        tofu plan   <-----+   revisar los cambios propuestos
             |            |
             v            |
        tofu apply -------+   ¿algo no cuadra? corrige y vuelve a plan
             |
             v
        tofu destroy      (al terminar la práctica)
```

### Qué ocurre por dentro en un `apply`

1. Se lee la configuración (`.tf`), **estado deseado**.
2. Se lee el estado (`tfstate`) y se **refresca** consultando la API real, **estado actual**.
3. Se calcula la diferencia y se construye el **grafo de dependencias**.
4. Se recorre el grafo, ejecutando en paralelo lo que no depende entre sí.
5. Se **actualiza el fichero de estado** con el resultado.

### Algunas opciones útiles

- `tofu plan -out=plan.out` y después `tofu apply plan.out`: garantiza que se aplica exactamente lo revisado.
- `tofu apply -target=recurso`: actúa solo sobre un recurso (útil para depurar, **no** para uso normal).
- `tofu apply -exclude=recurso`: lo contrario, deja un recurso fuera.
- `TF_LOG=DEBUG`: activa trazas detalladas, muy útiles para ver las llamadas HTTP reales al API de Proxmox.

## Buenas prácticas

1. **Nunca modificar a mano** en la web de Proxmox lo que gestiona OpenTofu: provocaremos estados *drift* (desviación entre estado real y estado guardado).
2. **Credenciales fuera del código**: usa variables de entorno (`TF_VAR_...`) o ficheros `.tfvars` excluidos del repositorio; en Proxmox, mejor **tokens de API** que la contraseña de `root`.
3. **`.gitignore` obligatorio**: `.terraform/`, `*.tfstate`, `*.tfstate.backup`, `*.tfvars` con secretos.
4. **Fijado de versiones** de OpenTofu y de los providers en el bloque `terraform`; el `.terraform.lock.hcl` sí se versiona.
5. **Lectura siempre el `plan`** antes de confirmar. Un `-/+` inesperado significa que una VM se va a destruir y recrear.
6. **Modulariza cuando se repita**: si se copia y pega un bloque tres veces, probablemente toque `for_each` o un módulo.

## Glosario rápido

- **IaC**: definir infraestructura mediante ficheros de código versionables.
- **Declarativo**: describir el resultado deseado, no los pasos.
- **Idempotencia**: repetir la operación no cambia el resultado.
- **Provider**: plugin que habla con la API de un sistema concreto.
- **Recurso**: objeto de infraestructura gestionado por OpenTofu.
- **Data source**: consulta de solo lectura sobre algo existente.
- **Estado**: inventario que enlaza configuración y realidad.
- **Drift**: divergencia entre lo declarado y lo que existe realmente.
- **Backend**: dónde se guarda el estado.
- **Módulo**: paquete reutilizable de configuración.
