# Administración de Proxmox VE: De la GUI a la Automatización con API

En nuestra experiencia de trabajo con Proxmox ya sabemos que la interfaz web de **Proxmox VE** es excelente para gestionar un puñado de nodos. Es intuitiva y visual, pero en entornos profesionales o producción masiva, "hacer clics" no escala. El verdadero potencial del administrador moderno no está en el ratón, sino en interactuar directamente con el **corazón de Proxmox: su API RESTful**.

A continuación exploraremos cómo saltar al siguiente nivel utilizando dos aproximaciones distintas pero complementarias: **Python** para una gestión puramente programática y **Bruno** para un flujo de trabajo basado en "recetas" o plantillas de red.

---

## Fundamentos: ¿Por qué una API REST?
Una API RESTful es una interfaz de programación de aplicaciones (API) que sigue los principios de la arquitectura **REST (Representational State Transfer)**, permitiendo que distintos sistemas se comuniquen a través del **protocolo HTTP** de forma sencilla, estandarizada y sin mantener estado entre las peticiones.

En una API RESTful, los recursos (por ejemplo, usuarios, máquinas virtuales o nodos) se identifican mediante URLs, y las operaciones sobre ellos se realizan utilizando los métodos estándar de HTTP:

* GET: obtener información de un recurso.
* POST: crear un nuevo recurso.
* PUT o PATCH: modificar un recurso existente.
* DELETE: eliminar un recurso.

Una característica fundamental de las APIs RESTful es que son stateless (sin estado): cada petición contiene toda la información necesaria para ser procesada, sin depender de peticiones anteriores. Además, normalmente intercambian datos en formatos como **JSON**, aunque también pueden utilizar XML u otros.

En el caso que nos ocupa podemos imaginar la **API RESTful** como una puerta de comunicación estandarizada que permite que otros programas "hablen" con Proxmox sin necesidad de una interacción directa. Proxmox utiliza el formato **JSON** como lenguaje principal para el intercambio de datos con el API, lo que facilita que cualquier herramienta moderna pueda leer y enviar datos.

### Los pilares del funcionamiento de la API:
*   **Recursos y Rutas:** Todo en Proxmox (una máquina virtual, un disco en Ceph o un nodo físico) es un recurso con una dirección única, similar a una URL. Por ejemplo: `/nodes/{node}/qemu/{vmid}`.
*   **Verbos HTTP:** Se utilizan órdenes estándar para definir la acción: **GET** para listar o leer, **POST** para crear (como un clonado), **PUT** para modificar y **DELETE** para borrar.
*   **Tareas Asíncronas (UPID):** Muchas operaciones (como crear un disco de 100GB) no son instantáneas. La API responde con un **UPID** (identificador único de tarea), que las herramientas externas deben monitorizar para saber cuándo ha terminado el proceso.

Proxmox VE utiliza una arquitectura **Multi-Master** donde todos los nodos comparten la configuración mediante el sistema de archivos **pmxcfs**. Debajo de la interfaz que conocemos todo lo que ocurre se traduce en llamadas a una API basada en **JSON**.

### El concepto de "Stateless" y los API Tokens
Para automatizar, no podemos depender de sesiones de navegador que caducan. Necesitamos una forma de identificarnos que sea segura y persistente. Proxmox implementa para ello los denominados como **API Tokens**, cuyas características principales son:

*   **Acceso Stateless:** No mantienen una sesión abierta; cada petición lleva su identificación.
*   **Seguridad Granular:** Se pueden crear tokens con privilegios limitados (separación de privilegios) para que un script solo pueda, por ejemplo, arrancar máquinas pero no borrarlas.
*   **Independencia:** Si un token se compromete, se revoca sin necesidad de cambiar la contraseña del usuario `root`.

## Acceso al API mediante Python y la librería `proxmoxer`
Python es el lenguaje rey de la automatización en infraestructuras. Para interactuar con Proxmox, utilizamos la librería **`proxmoxer`**, que actúa como un "wrapper" o envoltorio. En lugar de gestionar directamente peticiones HTTP complejas, tratamos los recursos de Proxmox como si fueran objetos de Python.

### El enfoque programático e imperativo
Utilizar Python es ideal cuando el despliegue requiere **lógica inteligente**. Es decir, cuando el "qué hacer" depende de condiciones variables:

1.  **Conexión Dinámica:** El script se conecta usando el host y el token definido en archivos de configuración.
2.  **Lógica de Decisión:** Puedes programar condicionales: "Busca el nodo con menos carga de CPU y despliega allí la nueva VM".
3.  **Gestión de Tareas Asíncronas (UPID):** Las operaciones en Proxmox (como clonar un disco de 100GB) no son instantáneas. La API devuelve un **UPID** (Unique Process ID). Un script de Python bien hecho monitoriza este ID mediante un bucle, esperando a que el estado pase a "stopped" y el "exitstatus" sea "OK" antes de seguir con el siguiente paso.
4.  **Integración de Cloud-Init:** Python permite inyectar configuraciones personalizadas de **Cloud-Init** (IPs, usuarios, llaves SSH) de forma masiva para que la VM esté operativa al primer arranque.

## Acceso mediante Bruno y el paradigma "Git-Native"
Otro enfoque distinto al anterior se basa en la herramienta **Bruno**, un cliente de API de código abierto que ha nacido como respuesta a la excesiva complejidad de herramientas como Postman. Su filosofía es **local-first**: no sube nada a la nube.

### El enfoque de "Templating" y Recetas
A diferencia de Python, donde "programamos" el comportamiento, en Bruno creamos **recetas reusables**. Su punto fuerte es el **templating de acciones REST**:

*   **Variables y Entornos:** En un archivo de entorno (ej. `lab.bru`), defines valores como `{{HOST}}`, `{{TOKEN}}` o `{{NODE}}`. Las peticiones al API, por ejemplo la creación o borrado de una MV, usan estas etiquetas en lugar de valores fijos.
*   **Colecciones como Código:** Cada petición (Encender, Apagar, Clonar, Borrar, etc.) es un pequeño archivo de texto plano con extensión `.bru`. Estos archivos de texto `.bru` de acciones puntuales pueden ser agrupadas, dentro de un mismo directorio, en una **Colección** relacionada con una funcionalidad concreta. Esto permite que toda la "caja de herramientas" de administración se guarde en un repositorio **Git**, permitiendo el control de versiones y la colaboración.
*   **Scripting ligero:** Aunque Bruno puede utilizarse de modo visual, permite inyectar lógica mediante **JavaScript**. Puedes programar que, tras recibir la respuesta de una creación de VM, Bruno extraiga automáticamente el UPID y lo guarde en una variable de colección para que la siguiente petición (Status) sepa qué tarea consultar sin que tú tengas que copiar y pegar nada.

**Uso ideal:** Bruno es perfecto para procesos de colaboración operativa. Si puntualmente un técnico o administrador necesita, por ejemplo, saber cómo borrar una VM, solo tiene que abrir la colección de Bruno y ejecutar la receta correspondiente.

## Comparativa de los enfoques: Python vs. Bruno
Para entender qué herramienta elegir, podemos compararlas según su uso:

| Característica | Python (`proxmoxer`) | Bruno (REST Client) |
| :--- | :--- | :--- |
| **Estilo** | Programación pura (Imperativo). | Declarativo / Recetas (Funcional). |
| **Flujo de trabajo** | Scripting y automatización total. | Herramientas operativas y testing. |
| **Manejo de Datos** | Lee YAML/JSON y procesa lógica. | Usa variables de entorno y visuales. |
| **Complejidad** | Requiere saber programar. | Intuitivo y rápido de aprender. |
| **Portabilidad** | Depende de librerías instaladas. | "Git-Native", basta clonar el repo. |

## Aplicación práctica en el Laboratorio
Trabajaremos a nivel práctico en escenarios prácticos que actuarán sobre nuestro clúster mediante las aproximaciones descritas:

*   **Con Bruno:** Tendremos carpetas organizada por fases o tareas: `/create`, `/start`, `/stop` y `/delete`. Podemos probar las distintas acciones accediento al directorio en el que residen los directorios anteriores y ejecutar las acciones correspondientes mediante un comando de CLI, o mediante la ejecución de un entorno Bruno.Es ágil para pruebas unitarias.
*   **Con Python:** Usaremos un script que debe desplegar N servidores. El script lee variables de entorno de un archivo, genera los N clones de una plantilla de MV, les asigna una IP estática diferente a cada uno vía Cloud-Init y los enciende, enviando un informe final.

##  Otras alternativas en el ecosistema
Aunque Python y Bruno cubren muchas de las necesidades del administrador, existen otras herramientas de "nivel experto" con escalabilidad y alcance superior, pero más complejas, que trataremos más adelante:

*   **Ansible:** Es la herramienta de **Infraestructura como Código (IaC)**. Utiliza módulos específicos para Proxmox que llaman a la API internamente. En lugar de un script, tomará un archivo YAML con el "estado deseado" (ej: "Quiero que haya 3 VMs encendidas con esta configuración") y Ansible se encarga del resto.
*   **Terraform/Opentofu:** Muy similar a Ansible pero más enfocado en el aprovisionamiento inicial de recursos (crear la infraestructura base).

## Conclusión
Dominar la API de Proxmox VE es necesario para tareas de administración avanzada. Ya sea usando el control total de **Python** para despliegues masivos condicionales o la agilidad de **Bruno** para por ejemplo herramientas de diagnóstico diario, el objetivo es el mismo: que la infraestructura trabaje para nosotros, y no al revés.
