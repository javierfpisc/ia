# Implementación de Ceph en Proxmox VE

## Introducción
La implementación de **Ceph** dentro de un clúster de Proxmox VE permite transformar los nodos de computación en un sistema de almacenamiento distribuido e hiperconvergente.

En este modelo:

* Los recursos de almacenamiento se integran directamente en el hipervisor
* Se facilita la escalabilidad
* Se permite una gestión unificada desde la misma interfaz

Anteriormente vimos que un clúster de Proxmox unifica la **configuración** y la **gestión**, pero **no comparte los discos**: por defecto cada VM vive en el disco local de su nodo. Eso impide dos elementos clave para la disponibilidad de nuestros entornos virtualizados:

- **Migrar una VM en caliente** (`qm migrate`) de un nodo a otro.
- **Alta disponibilidad (HA)**: que una VM se reinicie sola en otro nodo si el servidor se cae.

Para poder disponer de las funcionalidades anterioresr necesitamos **almacenamiento compartido**. Tradicionalmente sería una cabina o un servidor **NFS/iSCSI** externo (un único punto de fallo y un cuello de botella). **Ceph es la alternativa "hiperconvergente"**: el almacenamiento compartido lo forman los **propios discos de los nodos del clúster**, sin hardware adicional.

```
Sin Ceph: 3 servidores + 1 cabina/SAN → almacenamiento centralizado
Con Ceph: 3 servidores (cada uno con sus discos) → almacenamiento distribuido
```

El paradigma deseado se denomina **HCI (Hyper-Converged Infrastructure)**: VMs y almacenamiento conviven en los mismos nodos.

## ¿Qué es Ceph?
**Ceph** es un sistema de almacenamiento **distribuido, software-defined y sin punto único de fallo**. En Proxmox se usa principalmente en su modalidad de **bloque** (RBD) para alojar los discos de las VMs y los contenedores, aunque como veremos también es posible utilizarlo en modo CephFS (Ceph Filesystem).

**La idea fundamental es**: en lugar de "un disco grande y fiable", Ceph junta **muchos discos normales** y garantiza la fiabilidad **replicando los datos entre nodos**. Si se rompe un disco o se apaga un servidor, los datos siguen accesibles en las otras copias.

### Componentes clave

| Componente | Función | Mínimo recomendado |
|---|---|---|
| **MON** (*Monitor*) | Mantiene el mapa del clúster y el **quórum** de Ceph | 3 (número impar) |
| **MGR** (*Manager*) | Métricas, estadísticas, módulos (dashboard, etc.) | 2 (activo/pasivo) |
| **OSD** (*Object Storage Daemon*) | **Uno por disco físico**: almacena, replica y recupera datos | 3 (uno por nodo) |
| **MDS** (*Metadata Server*) | Solo necesario si usas **CephFS** (sistema de ficheros) | 0 en nuestro caso por ahora |
| **Pool** | Agrupación lógica donde se guardan los objetos; define el nº de réplicas | — |
| **RBD** (*RADOS Block Device*) | Disco de red que se asocia a una VM como si fuera un disco virtual | 1 pool tipo rbd |
| **CRUSH** | Algoritmo que decide **dónde** va cada copia (racks, hosts, discos) | — |

### Las tres réplicas
Por defecto se opera con los siguientes parámetros (que pueden redefinirse), `size = 3` y `min_size = 2`: **cada bloque se guarda 3 veces** en OSDs distintos (normalmente uno por nodo). **Capacidad útil ≈ capacidad bruta / 3.** Si cada nodo aporta 1 TB, tendrás ~1 TB útiles, no 3 TB. Es el "peaje" de la alta disponibilidad.

En Ceph, estos dos parámetros determinan **cuántas réplicas de los datos se mantienen y cuántas deben estar disponibles para que el pool pueda seguir aceptando escrituras**.

`size = 3` significa que cada objeto de datos tendrá **3 copias** distribuidas entre diferentes OSD según las reglas de CRUSH.
```text
Objeto A
 ├── copia → OSD 1
 ├── copia → OSD 5
 └── copia → OSD 9
```
Si un OSD falla, Ceph queda temporalmente con 2 copias y tratará de crear una tercera en otro OSD.

`min_size = 2` indica que deben existir **al menos 2 réplicas disponibles para que Ceph permita escrituras**.

| Situación    | Copias disponibles | ¿Se puede escribir? |
| ------------ | -----------------: | ------------------- |
| Normal       |                  3 | Sí                |
| Falla 1 OSD  |                  2 | Sí                |
| Fallan 2 OSD |                  1 | No                |
| Fallan 3 OSD |                  0 | No                |

**Configuración del ejemplo**:

```text
size = 3
min_size = 2
```

Inicialmente:
```text
        PG
      /  |  \
    OSD1 OSD2 OSD3
      ✓    ✓    ✓
```
Si falla `OSD3`:
```text
        PG
       /  \
    OSD1  OSD2
      ✓     ✓
```
Quedan **2 de las 3 réplicas**, por lo que Ceph puede seguir aceptando escrituras porque:
```text
copias disponibles = 2
min_size = 2
```
Ceph intentará recuperar la tercera copia en otro OSD:

```text
        PG
      /  |  \
    OSD1 OSD2 OSD4
      ✓    ✓    ✓
```
Y el objeto vuelve a tener 3 réplicas.

**En resumen**:
```text
size=3      → Ceph mantiene 3 copias de los datos.
min_size=2  → necesita al menos 2 copias disponibles para escribir.
```
Por tanto, `size=3 min_size=2` permite **perder una réplica/OSD y continuar trabajando**, mientras que si solo queda una réplica, Ceph **deja de aceptar escrituras** hasta recuperar suficiente redundancia.

## Preparación del almacenamiento
La preparación de discos físicos adicionales es un requisito esencial para Ceph, ya que este sistema requiere **dispositivos de bloque dedicados**.

### Requisitos clave
Los dispositivos utilizados como base deben de cumplir:

* Discos sin formato previo
* Uso exclusivo para Ceph
* Evitar sistemas de archivos locales intermedios

En la siguiente tabla vemos los requisitos mínimos y recomendados

| Recurso | Mínimo | Recomendado en producción |
|---|---|---|
| Nodos | **3** (imprescindible) | 3–5+ |
| Red para Ceph | 1 GbE dedicada (suficiente para practicar) | **10 GbE o más**, red separada de corosync y de la de gestión |
| Discos por nodo | 1 disco extra dedicado (puede ser un SSD o un segundo disco virtual) | 1–4 OSDs; NVMe/SSD para DB/WAL si los OSD son HDD |
| RAM | +2–4 GB por nodo para los OSD | ~1 GB de RAM por TB de OSD, más lo de las VMs |
| CPU | 2–4 cores | Más cores si hay mucha escritura |

Reglas de oro:

1. **El disco del sistema no debe ser OSD.** Cada OSD necesita un disco (o partición) exclusivo.
2. **El nombre del clúster y la red deben ser estables**: cambiar la IP de la red de Ceph después obliga a reconfigurar los MON.
3. **No compartas la red de Ceph**: la replicación puede saturar el enlace y provocar caídas de quórum (corosync es muy sensible a la latencia).
4. Si no tienes servidores con discos libres, **no montes Ceph**: usa NFS desde un NAS o almacenamiento local + **replicación**.

### Objetivo
Al añadir los discos físicos como OSDs en cada nodo:

* Se establece la infraestructura física del clúster
* Se permite la **distribución de datos**
* Se habilita la **redundancia entre nodos**

## Inicialización del clúster
La herramienta `pveceph` permite desplegar los servicios fundamentales del sistema.

### Componentes principales del clúster
Será necesario definir y operar los siguientes componentes para que el clúster funcione

#### MON (Monitor)

* Mantiene el estado del clúster
* Gestiona los mapas de distribución
* Coordina los nodos

#### MGR (Manager)

* Proporciona métricas de rendimiento
* Gestiona tareas de orquestación
* Supervisa el estado en tiempo real

## OSD (Object Storage Daemons)
La creación de los OSD, asociados a un dispositivo físico, representa la activación de la capa de datos.

### Características

* Cada OSD gestiona un disco físico
* Maneja:
    * Lectura
    * Escritura
    * Replicación

### En un clúster de 3 o más nodos
Las ideas detrás de la utilización de varios de nodos son:

* Se pueden desplegar múltiples OSD por nodo
* Se implementará una distribución equilibrada de datos
* Se dispone de mayor tolerancia a fallos

## Pools y Placement Groups (PGs)
Los Pools y PGs definen la estructura lógica del almacenamiento. 

### Pools
Un pool de Ceph es un contenedor lógico de almacenamiento dentro del cluster donde se almacenan los objetos (datos).

* Cada pool define cómo se replican o distribuyen los datos entre los OSDs.
* Los volúmenes RBD, librerías de objetos o discos de VM se crean dentro de un pool.
* Puedes tener varios pools con diferentes políticas de replicación, tamaños de PG, QoS, etc.

### Placement Groups (PGs)
Son estructuras lógicas en Ceph que permiten:

* Distribuir los objetos entre OSDs
* Impactar directamente en el rendimiento
* Balanceo de carga

### Configuración recomendada
Será muy dependiente del contexto, en caso de un clúster de 3 nodos con 6 OSDs podemos establecer:

* Tamaño de réplica: **3** (número total de réplicas de cada objeto)
* Tamaño mínimo: **2** (número mínimo de réplicas necesarias para operar)

### Resultado

* Tolerancia a la caída de un nodo completo
* Escrituras seguras solo si hay suficientes copias
* Integridad de datos garantizada

## Integración con Proxmox
La integración se realiza mediante almacenamiento tipo **RBD (Rados Block Device)** usando `pvesm`.

### Beneficios

* Uso del pool como almacenamiento de VMs
* Soporte para contenedores
* Integración completa con Proxmox

### Capacidades avanzadas

* Migración en vivo (live migration)
* Alta disponibilidad (HA)
* Escalabilidad horizontal

## Resumen

La integración de Ceph en Proxmox permite:

* Crear un sistema hiperconvergente
* Distribuir datos de forma eficiente
* Garantizar alta disponibilidad
* Simplificar la gestión del almacenamiento
