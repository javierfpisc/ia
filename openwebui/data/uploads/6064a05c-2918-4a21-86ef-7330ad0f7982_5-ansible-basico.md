# Interacción con MVs en Proxmox usando Ansible  
En esta primera práctica con Ansible vamos a aprender a gestionar máquinas virtuales (MVs) desplegadas con OpenTofu en Proxmox mediante Ansible, realizando tareas básicas de automatización.

## Requisitos Previos

- **Infraestructura**:  
  - MVs ya creadas en Proxmox con OpenTofu, algo que ya hemos hecho en las prácticas anteriores.  
  - Acceso SSH mediante claves públicas configuradas (usuario `ansible_user` con permisos sudo).

- **Software**:  
  - Ansible instalado en la máquina de control, lo haremos en nuestro equipo de trabajo.  
  - Inventario básico en formato YAML o INI, el cual crearemos en esta práctica.  

---

## Instalación de Ansible
La instalación de Ansible es tremendamente sencilla ya que el paquete se encuentra en los repositorios oficiales de Debian. Por tanto, ejecutamos:
```bash
sudo apt update
sudo apt install -y ansible
```
Tras la instalación testeamos con el comando `ansible --version` y podemos lanzar un sencillo test a nuestro equipo local utilizando el **módulo ping** con el comando `ansible -m ping localhost`.

## Configuración del Inventario  
Editaremos el archivo `inventory.yml` dentro de la ruta **tools/ansible/basico**:  
```yaml
all:
  hosts:
    vm1:
      ansible_host: 192.168.56.71  # IP de la MV1 en Proxmox
      ansible_user: debian
    vm2:
      ansible_host: 192.168.1.72   # IP de la MV2 en Proxmox
      ansible_user: debian
  children:
    debian_servers:  # Grupo para todas las VMs
      hosts:
        vm1:
        vm2:
```
!!!Nota
    Para poder comunicarnos con las 2 máquinas del inventario anterior es necesario que éstas existan y tengan una IP asignada. Este requisito se materializa en uno de los ejercicios de OpenTofu, concretamente el relacionado con la infraestructura **tools/opentofu/infra-proxmox-1**. Si no se ha completado el ejercicio podéis simplemente acceder a dos máqinas de vuestra infraestructura y asignarle las IPs anteriores de forma manual. También es importante comprobar cual es la IP de la puerta de enlace (gateway) de la configuración de red, ésta debería estar establecida a la IP de la interfaz del bridge **vbrm0** en Proxmox.
    
    También es posible establecer la configuración desde la WebUI de Proxmox, en la sección Cloud-Init de las propiedades de la MV (pero para que funcione no debe de usarse archivo de configuración cloud-init en el despliegue).

### Explicación
**vm1 y vm2** son los nombres que Ansible utilizará para identificar cada máquina. Las variables definidas para cada host son autoexplicativas:

- `ansible_host`: Dirección IP de la MV.  
- `ansible_user`: Usuario con acceso SSH.

Menos evidente, pero también bastante obvia, es la estructura de agrupación del archivo. La estructura es jerárquica y se divide en hosts y grupos:

* **all**: grupo raíz que contiene todos los equipos del inventario.
* **hosts**: define las máquinas individuales.
* **children**: bloque que permite crear subgrupos dentro de all.
* **debian_servers**: grupo específico que contiene vm1 y vm2. En este caso coinciden los miembros del grupo con todos los hosts (all), pero por supuesto no tiene porque ser así. Podemos crear todos los grupos que deseemos.

## Comprobación de Conexión  
Ejecutamos, desde el directorio en que reside el archivo del inventario, el siguiente comando para verificar que Ansible puede conectarse a las MVs:
```bash
ansible all --private-key ../../keys/id_lab_ed25519 -m ping -i inventory.yml
```
**El comando anterior:** Ejecuta, a través del módulo ping de Ansible, un ping contra todos (all) los hosts del inventario, utilizando para la conexión con éstos la clave privada ssh, vinculada con la pública que ya está incorporada en los hosts a través del despliegue.

!!!Importante
    Para que la conectividad ssh sea posible debemos de haber entrado a los hosts manualmente al menos una vez para aceptar el fingerprint, de lo contrario la conexión fallará.
  
**Salida esperada**:
```json
vm1 | SUCCESS => { "changed": false, "ping": "pong" }
```

## Playbook para Tareas Básicas  
Crearemos un playbook llamado `tasks.yml` en el directorio **tools/ansible/basico** con el contenido:
```yaml
---
- name: Tareas básicas de mantenimiento
  hosts: debian_servers
  become: yes  # Usar privilegios sudo

  tasks:
    - name: Actualizar caché de paquetes
      apt:
        update_cache: yes

    - name: Actualizar todos los paquetes (security + bugfixes)
      apt:
        upgrade: dist  # Opciones: 'dist' (solo seguridades), 'yes' (todo)

    - name: Auditoría de usuarios con acceso SSH
      shell: "grep '^ssh' /etc/group | cut -d: -f4"
      register: ssh_users
      changed_when: false  # No marca como "changed" (solo auditoría)

    - name: Mostrar resultados
      debug:
        msg: "Usuarios con acceso SSH: {{ ssh_users.stdout }}"
```

### Explicación
Veremos como a través de los módulos de Ansible, que son los que nos dan garantía de su comportamiento idempotente, ejecutaremos la siguiente lista de tareas:

- **Actualizar caché**: Equivalente a `apt update`.  
- **Actualizar sistema**: Aplicará actualizaciones de seguridad (`upgrade: dist`).  
- **Auditoría**: Identifica usuarios con permiso SSH (sin modificar el sistema).  

El encabezado del archivo contiene la información de contexto relevante:

- **name** del playbook
- **hosts** del inventario a los que se aplicarán las task del playbook, en este caso a todos los miembros del grupo **debian_servers**
- **become** establecido a **yes** indica que la ejecución de comandos que la requieran utilizarán el mecanismo sudo (el usuario por tanto debe de ser sudoer, en nuestro caso sí lo es)

#### Tareas
El concepto de tarea (task), por ser el más común y flexible en cuanto a su definición, requiere un poco más de explicación. Una tarea (task) representa una acción que Ansible debe ejecutar sobre uno o varios hosts. Generalmente, una tarea tiene la siguiente estructura:
```yaml
- name: Descripción de la tarea
  modulo:
    parametro1: valor1
    parametro2: valor2
```
Por ejemplo:
```yaml
- name: Instalar el paquete htop
  ansible.builtin.apt:
    name: htop
    state: present
```
Una tarea está formada principalmente por:

* **Name**: descripción de la tarea. Se utiliza para identificarla y mostrar información durante la ejecución del playbook.
* **Módulo**: indica qué acción realizará Ansible. En este caso se utiliza ansible.builtin.apt, encargado de gestionar paquetes en sistemas basados en Debian.
* **Parámetros del módulo**: permiten configurar cómo se ejecutará la acción.

En el ejemplo anterior el parámetro `name` indica el paquete sobre el que se actuará y el parámetro `state` indica el estado deseado del paquete.
Es importante tener en cuenta que la estructura y los parámetros disponibles dependen del módulo utilizado. Cada módulo define su propia interfaz y los parámetros que admite. Por ejemplo, el módulo apt acepta parámetros relacionados con la gestión de paquetes:
```yaml
ansible.builtin.apt:
  name: htop
  state: present
  update_cache: yes
```
Mientras que el módulo file utiliza una interfaz diferente, adaptada a la gestión de archivos y directorios:
```yaml
ansible.builtin.file:
  path: /opt/demo
  state: directory
  mode: "0755"
```
Por tanto, aunque todas las tareas siguen una estructura general similar, los parámetros que podemos utilizar vienen determinados por la interfaz definida por el módulo empleado.

## Ejecución del Playbook
Antes de ejecutar el playbook hay que tener en cuenta que debemos de gestionar la autenticación en los hosts. Para ello usaremos, como antes, la autenticación mediante claves ssh. Por tanto indicaremos, mediante una directiva del archivo de inventario, la ruta hacia la clave privada utilizada para la autenticación ssh. Simplemente añadimos al archivo de inventario las líneas (la indentación debe de estar a la altura del bloque hosts):
```bash
  vars:
      ansible_ssh_private_key_file: ../../keys/id_lab_ed25519
```
A continuación ejecutamos el playbook:
```bash
ansible-playbook -i inventory.yml tasks.yml
```

**Salida esperada**: La salida sería algo como lo siguiente:
```yaml
TPLAY [Tareas básicas de mantenimiento] ******************************
TASK [Gathering Facts] ***********************************************
ok: [vm1]
ok: [vm2]
TASK [Actualizar caché de paquetes] **********************************
ok: [vm2]
ok: [vm1]
TASK [Actualizar todos los paquetes (security + bugfixes)] ***********
ok: [vm2]
ok: [vm1]
TASK [Auditoría de usuarios con acceso SSH] **************************
ok: [vm2]
ok: [vm1]
TASK [Mostrar resultados] ********************************************
ok: [vm1] => {
    "msg": "Usuarios con acceso SSH: "
}
ok: [vm2] => {
    "msg": "Usuarios con acceso SSH: "
}
PLAY RECAP ***********************************************************
vm1                        : ok=5    changed=0    unreachable=0 \
failed=0    skipped=0    rescued=0    ignored=0   
vm2                        : ok=5    changed=0    unreachable=0 \
failed=0    skipped=0    rescued=0    ignored=0   
```
En la salida anterior podemos ver el resultado de la ejecución de cada una de las tareas, task, del playbook de Ansible. Al final se muestra un resumen de la ejecución del playbook, indicando las estadísticas de la ejecución para cada host:

* **ok**: número de tareas que han terminado correctamente
* **failed**: tareas que han fallado
* **rescued**: Indica que una tarea falló, pero el error fue capturado mediante un bloque rescue
* **ignored**: Indica que una tarea falló, pero se le dijo explícitamente a Ansible que ignorase el error con una claúsula **ignore_erros** en el playbook
* **unreachable**: indicaría si el host no ha podido ser contactado
* **skipped**: tareas que han saltado u omitido por algún motivo, como por ejemplo una condición establecida
* **changed**: indica si el host ha sufrido algún cambio tras la ejecución del playbook
